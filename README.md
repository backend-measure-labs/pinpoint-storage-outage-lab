# pinpoint-storage-outage-lab

핀포인트 서버(컬렉터 · HBase)가 장애일 때 에이전트를 붙인 Spring 앱의 연결 · 스레드 · 메모리가 어떻게 변하는지 재현해 측정한 랩입니다.

## 요약

**핀포인트 장애 넷 모두에서 앱에 커넥션 · 스레드 · 메모리가 쌓이지 않았습니다.** 같은 조건 2회차가 같은 결과를 냈습니다.

- 앱이 받은 연결 · 처리 중 요청 · 요청 처리 시간은 장애 중에도 정상 구간과 같았습니다 (받은 연결 최대 51~55, 요청 평균 5.6~6.0ms, 오류 0).
- 에이전트는 장애를 겪었습니다. 전송 실패 경고를 남겼고, 컬렉터로 가는 연결이 컬렉터 다운에서 0개, 컬렉터 응답 없음에서 5개로 바뀌었습니다. 장애가 이어지는 동안 그 수가 늘지 않았고 앱 요청 경로에 번지지 않았습니다.
- 장애 중 재기동도 정상 재기동과 같았습니다 (기동 CPU 5.3~7.0초, 재연결 폭주 없음).
- 앱 메모리 최대는 RSS 329MB 로 파드 request 1Gi 의 32% 였습니다. 스레드 수가 같은데 스레드 스택이 최대 14MB 커진 파드가 있었습니다. 장애와의 인과는 확인되지 않았고, 장애가 이어져도 더 늘지 않았습니다(4.4).

→ 「핀포인트 장애가 앱에 커넥션을 물려 메모리를 키웠다」는 추정은 이 재현에서 성립하지 않습니다.

## 1. 목적

**과거에 「핀포인트 장애가 앱에 커넥션을 물려 메모리를 키웠다」고 추정한 원인이 맞는지 재현으로 판정합니다.**

쿠버네티스에 올린 Spring 서비스들의 노드가 반복해서 죽던 때가 있었습니다. 당시 모든 서비스에 핀포인트 에이전트가 붙어 있었고, 핀포인트 서버에서는 세 가지 장애가 실제로 일어났습니다: 컬렉터 다운, HBase 락 타임아웃, HBase 다운. 원인을 핀포인트로 추정해 TTL 조정 · 테이블 정리 같은 조치를 하다가 결국 핀포인트를 걷어냈고, 원인은 확인하지 못했습니다.

| 질문 | 판정에 쓰는 비교 |
|---|---|
| ① 핀포인트 장애 때문에 앱에 커넥션이 물리는가 | 정상 ↔ 장애 넷 (아래 「장애」) |
| ② 물린다면 무엇이 쌓이는가 | 장애끼리, 그리고 장애 중 재기동 ↔ 정상 재기동 |
| ③ 아니라면 남는 원인 후보는 무엇인가 | 이 랩이 배제한 범위와 배제하지 못한 범위 |

**판정 기준 (실행 전에 정함)**

장애 구간에서 아래 중 하나라도 정상 구간보다 늘고, 장애를 걷으면 돌아오면 「물린다」로 판정합니다.

| 지표 | 왜 보나 |
|---|---|
| 앱이 받은 연결 · 처리 중 요청 · 요청 처리 시간 | 「요청이 쌓여 커넥션이 늘었다」는 원래 추정을 그대로 잰다. |
| 컬렉터로 가는 연결 수 (상태별) | 재연결이 쌓이는가 |
| 스레드 수 (핀포인트 · Tomcat) | 연결 · 요청을 붙잡는 것은 결국 스레드다. |
| RSS · 힙 · 네이티브 메모리 구역 | 무엇이 쌓였는지 구역으로 나눈다. |

## 2. 조건

### 알아야 할 용어

| 용어 | 뜻 |
|---|---|
| 에이전트 | 앱 JVM 에 `-javaagent` 로 붙어 요청을 추적하고, 추적 · 통계 데이터를 컬렉터로 보내는 핀포인트 구성 요소 |
| 컬렉터 | 에이전트가 보낸 데이터를 받아 HBase 에 저장하는 서버. 에이전트와 gRPC 로 연결합니다(9991 에이전트 · 9992 통계 · 9993 스팬). |
| HBase | 핀포인트의 저장소. 리전 서버가 실제 읽기 · 쓰기를 맡습니다. |
| RSS | 프로세스가 실제로 쓰는 물리 메모리. 쿠버네티스의 메모리 압박은 이 값에서 옵니다. |
| NMT | JVM 네이티브 메모리 추적(`-XX:NativeMemoryTracking`). 힙 밖의 메모리를 구역(Thread · Other 등)으로 나눠 보여 줍니다. gRPC 전송의 네티 버퍼는 Other 에 잡힙니다. |
| QoS Burstable | 쿠버네티스에서 request 는 있고 limit 은 없는(또는 다른) 파드. 노드 메모리가 허락하는 만큼 늘 수 있습니다. |

### 장애

원래 운영에서 확실히 일어난 장애 셋을 넣습니다. 컬렉터 다운은 두 모습으로 나눕니다.

| 장애 | 재현 방법 | 컬렉터 · 에이전트가 겪는 것 |
|---|---|---|
| 컬렉터 다운 (프로세스 없음) | 컬렉터 디플로이먼트를 0개로 | 연결 거부. 에이전트는 재연결을 반복합니다. |
| 컬렉터 다운 (응답 없음) | 컬렉터 컨테이너 일시정지 | 커널이 TCP 연결을 받지만 컬렉터는 읽지 않습니다. 에이전트의 채널 쓰기 버퍼(채널당 32MB)가 찰 수 있는 것은 이쪽뿐입니다. |
| HBase 락 타임아웃 | HBase 파드에서 컬렉터로 가는 패킷만 15초 늦춤 (`tc netem`) | 리전 서버는 살아 있고, 컬렉터의 HBase 쓰기마다 타임아웃(10초)이 납니다. |
| HBase 다운 | 리전 서버 프로세스 강제 종료 | 컬렉터의 HBase 쓰기가 실패합니다. 마스터 · ZooKeeper 는 그대로입니다. |

**HBase 락 타임아웃을 컨테이너 일시정지로 재현하지 않은 이유:** 일시정지가 ZooKeeper 세션 상한(이 구성에서 40초)을 넘기면 리전 서버가 스스로 종료해 「멈췄다가 다운」이 됩니다. 컬렉터 입장의 락 타임아웃은 「리전 서버는 살아 있는데 쓰기가 타임아웃으로 끝난다」이므로, 컬렉터의 HBase 타임아웃(10초)보다 늦게 응답이 오게 만들었습니다.

### 단계 길이

| 단계 | 길이 | 근거 |
|---|---|---|
| 정상 | 300초 | 에이전트 통계 전송 묶음(5초 수집 × 6) 30초의 10회분 |
| 장애 유지 | 420초 | 에이전트의 가장 긴 타이머인 전송 불가 대기(`not-ready-timeout`) 300초에 keepalive 판정(30초 + 60초)과 여유를 더했습니다. |
| 장애 중 재기동 | 240초 | gRPC 재연결 대기 상한 120초의 두 바퀴 |
| 복구 | 180초 | 재연결 대기 상한 120초 + 안정 60초 |

길이는 「변화가 나타날 시간」이 아니라 「에이전트 타이머가 한 바퀴 이상 도는 시간」으로 정했습니다. 쌓이는 것이 있다면 타이머가 도는 동안 커져야 합니다.

## 3. 절차

### 한 회차

정상 → 정상 중 재기동 → 장애 넷 각각 「장애 유지 → 장애 중 재기동 → 복구」. 한 회차 약 66분, 같은 조건 2회. 3회를 계획했으나 2회가 모든 단계에서 같은 판정을 내 3회차는 하지 않았습니다(부록 C).

### 보는 지표

앱 안의 프로브가 2초마다 한 줄을 남깁니다(`app/src/main/java/lab/probe`). 바깥에서 `jstat` · `jcmd` 를 주기적으로 띄우면 그 JVM 의 기동 비용이 CPU 측정에 섞이므로 같은 프로세스 안에서 읽습니다.

| 지표 | 어떻게 얻나 |
|---|---|
| RSS · cgroup 메모리 | `/proc/self/status` · `/sys/fs/cgroup/memory.current` |
| 힙 · NMT 구역 | `MemoryMXBean` · `DiagnosticCommand vmNativeMemory summary` |
| 스레드 | 이름으로 나눠 셉니다(`Pinpoint-*` · `http-nio-*-exec-*`). |
| 컬렉터 연결 · 받은 연결 | `/proc/net/tcp(6)` 에서 원격 포트 9991~9993 은 상태별로, 로컬 8080 은 ESTABLISHED 만 |
| 요청 | 서블릿 필터에서 2초 구간의 건수 · 평균 · 최대 처리 시간 · 처리 중 최대 · 100ms 칸당 도착 최대 |
| 기동 | JVM 시작 시각(`RuntimeMXBean`)부터 첫 표본까지의 시간과 그때까지 쓴 CPU |

**100ms 칸당 도착 최대를 넣은 이유:** 요청 처리 시간이 튀었을 때 요청이 몰려 들어온 것(부하 쪽)인지, 고르게 들어왔는데 처리가 늦은 것(앱 쪽)인지를 나누기 위해서입니다. Tomcat 작업 스레드는 요청이 몰리면 늘고 바로 줄지 않아, 스레드가 는 단계에서 그 원인이 도착 몰림인지를 이 값으로 가립니다(4.2 의 1회차 컬렉터 복구). 이 값은 서블릿 필터에 들어온 시각으로 세고 주문 요청이 부르는 재고 자기 호출도 포함하므로, 앱이 잠깐 멈췄다 풀려도 몰림으로 보일 수 있습니다.

## 4. 결과

같은 조건으로 2회 실행했습니다. 표의 값은 「1회차 / 2회차」 순서입니다. 회차별 전체 표 · 로그 · 그래프는 `docs/results/` 에 있습니다.

### 4.1 장애가 실제로 걸렸는가

판정하기 전에, 앱 쪽이 평탄한 것이 「장애가 안 걸려서」가 아닌지 확인했습니다.

| 장애 | 컬렉터 · 에이전트 로그에 남은 것 (두 회차 모두 남음) |
|---|---|
| 컬렉터 다운 | 에이전트가 명령 스트림 실패(`UNAVAILABLE: io exception`)를 반복했습니다. 컬렉터로 가는 연결은 장애 직후 0개가 됐습니다(유지 단계 표본 210개 중 203개). 장애 중 재기동 뒤에는 연결 시도(SYN_SENT)가 표본 123 · 124개 중 4 · 4개에만 잡혔습니다(최대 4개). |
| 컬렉터 응답 없음 | 에이전트의 에이전트 정보 전송이 응답 대기 시간 초과로 끝났고(1회차는 장애 중 재기동 단계에서), keepalive 실패 경고가 남았습니다. |
| HBase 락 타임아웃 | 컬렉터 안의 HBase 클라이언트가 쓰기마다 메타 조회 락 10초 초과(`Failed to get user region lock`)와 호출 시간 초과를 남겼습니다. WARN · ERROR 가 장애 유지 단계에 206 · 213건, 장애 중 재기동 단계에 763건입니다. 장애 중 재기동 때 에이전트의 에이전트 정보 전송이 응답 대기 시간 초과로 5건 끝났습니다. |
| HBase 다운 | 컬렉터의 HBase 쓰기가 락 타임아웃과 같은 메시지(메타 조회 락 초과 · 재시도 소진)로 실패했습니다. 장애 유지 단계 208 · 202건입니다. 락 타임아웃과 가르는 것은 리전 서버 연결 거부(`failed on connection exception`, 대부분 INFO 라 summary.md 의 WARN · ERROR 표에는 없고 원본 로그에서 셈)입니다. 락 타임아웃 단계에는 없고, HBase 다운 유지 · 재기동 단계에 합계 26 · 26건, 이어진 복구 단계에도 남았습니다. HBase 컨테이너 메모리는 1.7GB 에서 0.36GB 로 내려갔습니다(리전 서버 종료, 1회차). 장애 중 재기동 때 에이전트의 에이전트 정보 전송이 응답 대기 시간 초과로 5건 끝났습니다. |

  - 컬렉터 다운: 장애 직후 0개가 됐습니다(표본 210개 중 203개). 장애 중 재기동 뒤에도 0개이고, 연결 시도(SYN_SENT)는 표본 4개에만 잡혔습니다.
  - 컬렉터 응답 없음: 5개입니다(표본 210개 중 172 · 169개). 같은 단계에 닫는 중인 소켓(그 밖의 상태)이 표본 39 · 36개에서 1~2개 잡혔습니다. 늘어난 1개가 새로 맺은 연결인지는 프로브로 가리지 못했습니다.
  - HBase 락 타임아웃 · HBase 다운: HBase 다운 행의 3개가 장애에 묶이는지는 가리지 못했습니다. 4개 중 1개가 빠지는 일이 파드 나이 약 385초(두 회차 4개 파드)와 604 · 605초(2개 파드)에 났고, 그중 4개는 장애를 걷은 해제 · 복구 단계에서였습니다. HBase 다운 단계는 직전 해제 단계에서 이미 3개가 된 파드가 이어진 것이고, 빠진 연결은 장애를 걷어도 돌아오지 않았습니다. 어느 채널인지는 프로브가 컬렉터 포트 셋을 합쳐 세서 가리지 못했습니다(부록 C).
  - 어느 장애에서도 장애가 이어지는 동안 늘지 않았습니다.

### 4.4 스레드 스택

4.2 의 표에서 스레드 수는 같은데 NMT Thread(스레드 스택의 커밋 크기)가 7MB 대에서 14~21MB 로 커진 경우가 있습니다. 장애 때문인지 가렸습니다.

| 관찰 | 값 |
|---|---|
| 늘어난 파드 | 2초 시계열이 있는 앱 파드 12개(회차마다 6개) 중 4개. 그 밖에 1개(2회차 컬렉터 다운 중 재기동)는 시작부터 2MB 높았고 관측 내내 ±2MB 를 오갔습니다. |
| 시작 때 걸려 있던 장애별 | 최초 기동 0/2 · 정상 재기동 0/2 · 컬렉터 다운 1/2 · 컬렉터 응답 없음 1/2 · HBase 락 타임아웃 0/2 · HBase 다운 2/2 |
| 늘어나는 모양 | 2초 표본 사이에 0.6~4.4MB 씩(0.5MB 이상 계단 기준) 불규칙한 계단으로 늘었습니다. 그동안 스레드 수 · Tomcat 스레드 · 힙 커밋 · GC 는 그대로였습니다. |
| 언제 | JVM 시작 뒤 약 110~310초 사이에 몇 번 늘고 멈췄습니다(0.5MB 미만 계단은 330초 무렵까지). 늘기를 멈춘 뒤에는 더 늘지 않았습니다. |
| 크기 | 파드당 최대 +14MB (request 1Gi 의 1.4%) |

- **판정:** 장애와 이 증가의 인과는 확인되지 않았습니다. 장애 없이 시작한 파드 4개는 늘지 않았고, 장애 중에 재기동한 파드는 8개 중 4개가 늘었습니다. 같은 장애에서도 늘기도 하고 안 늘기도 했습니다. HBase 다운 중 재기동만 따로 다시 한 실험(2초 시계열 없이 240초 한 시점)에서는 7.4MB 로, 같은 실험의 정상 재기동 7.3MB 와 같았습니다. 늘어난 뒤에는 장애가 이어져도 더 늘지 않아, 「장애가 길어지면 쌓인다」에 해당하지 않습니다.
- **기제 (가설):** 이 VM 의 커널은 THP(투명 huge page)가 `always` 이고, khugepaged 가 2MB 구간에서 4KB 페이지 하나만 쓰여도 huge page 로 합칠 수 있는 설정(`max_ptes_none=511`)입니다(`docs/results/env/kernel-thp.txt`, 회차 뒤 같은 VM 에서 읽음). 스택 구간이 huge page 로 합쳐지면 스레드 수가 그대로여도 스택 커밋이 늘 수 있습니다. 어느 스레드의 스택인지는 가리지 못했습니다. 따로 한 실험은 늘지 않아 짝지을 재료가 없었습니다.
- 운영 노드의 THP 설정은 이 랩에서 알 수 없습니다(부록 C).

```bash
scripts/track.sh 120                              # 진행 중 상태 확인 (읽기만)
```

- 실행 스크립트는 `rancher-desktop` 컨텍스트만 담은 kubeconfig 를 따로 만들어 쓰고, 노드 이름이 `lima-rancher-desktop` 이 아니면 아무것도 하지 않고 멈춥니다. 다른 환경이면 `LAB_CONTEXT` · `LAB_NODE` 로 지정합니다.
- 회차가 끝나면 디플로이먼트를 0개로 줄입니다. 네임스페이스는 지우지 않습니다. 정리: `kubectl --context "${LAB_CONTEXT:-rancher-desktop}" delete namespace pinpoint-lab`
- 이미지는 쿠버네티스가 Docker 런타임을 쓴다는 전제로 로컬 이미지(`imagePullPolicy: Never`)를 씁니다.

## 부록 C. 로컬 특수성

운영과 다른 점과 그 영향입니다. 판정에 영향을 줄 수 있는 것은 「영향」 칸에 적었습니다.

| 항목 | 이 랩 | 영향 |
|---|---|---|
| 클러스터 | Rancher Desktop k3s 단일 노드, VM 4코어 · 8GB | 노드 메모리 압박 · 파드 축출은 재현하지 않습니다. 이 랩의 질문은 「앱에 쌓이는가」이고, 쌓이지 않아 압박까지 갈 재료가 없었습니다. |
| 규모 | 앱 파드 1개 · 에이전트 1개 · 컬렉터 1개 | 에이전트 수십 개가 한 컬렉터에 붙은 규모는 재지 않았습니다. 5절의 「배제하지 못한 것」에 넣었습니다. 컬렉터 쪽 부하는 범위 밖입니다. |
| 핀포인트 서버 | 공식 이미지 2.5.3, HBase 독립 실행(HDFS 없음) · ZooKeeper 1대 | 운영 HBase 의 설정이 장애를 낸 원인 자체는 재현하지 않고, 장애의 결과(락 타임아웃 · 다운)를 주입했습니다. |
| JDK | Corretto 17 (alpine) | 운영 기본 이미지의 alpine 판에 arm64 가 없어 바꿨습니다. 같은 Java 17 · musl 입니다. |
| 부하 | k6 고정 도착률 | 고정 도착률이어도 100ms 칸에 도착이 몰리는 순간이 있습니다. 1회차 컬렉터 복구에서 도착이 100ms 에 17건까지 몰려 처리 중 요청이 12건이 됐고, Tomcat 작업 스레드가 기본 10개를 넘어 14개로 늘었습니다. 에이전트가 컬렉터에 다시 붙기 전에 난 일이라 판정에서 뺐습니다. |
| 시계 | VM 시계가 호스트보다 약 2.6초 늦음 | 회차마다 `clock.csv` 로 재고 분석에서 맞췄습니다. |
| 측정 결함 1 | 두 회차 이미지의 프로브 헤더에 열 이름 둘이 빠짐 | 값은 남았고 분석기가 이름을 채웁니다. 소스는 고쳤습니다. |
| 측정 결함 2 | 2회차의 서버 컨테이너 메모리 수집이 컬렉터 다운 중 재기동에서 멈춤 | 컨테이너가 조회 중에 사라지면 수집 루프가 끝나던 결함입니다. 고쳤고, 서버 쪽 메모리는 1회차 값을 씁니다. |
| 커널 | THP `always` · khugepaged `max_ptes_none=511` | 스레드 스택이 커진 일(4.4)의 가설입니다. 운영 노드의 설정은 모릅니다. |
| 프로브 | 컬렉터 연결을 포트 셋(9991~9993)을 합쳐 상태별로 셈 | 파드 나이 385 · 604초 무렵에 빠진 연결 1개가 어느 채널인지 가리지 못했습니다. 줄어든 것이라 「쌓이는가」의 판정에는 영향이 없습니다. |
| 회차 | 2회 (3회 계획) | 2회가 모든 단계에서 같은 판정이었고, 3회차가 판정을 바꿀 여지가 없어 하지 않았습니다. |
